# Звіт. Лабораторна робота 1, варіант 12: епізод госпіталізації (`/admissions`)

Стек: Python 3.12, FastAPI, psycopg 3 з пулом, PostgreSQL 16, nginx 1.27, Docker Compose.
Параметри варіанта: фінальний образ `python:3.12-slim`, ліміти сервісу 1 CPU / 512 МБ,
додаткова вимога: healthcheck без curl і wget в образі.

> Поля `⟨ЗАПОВНИТИ⟩` заповнюються після прогонів на вашій машині; жодне число нижче не вигадане.

## 1. Схема таблиці

Таблиця `admissions` (файл `db/init.sql`, накочується автоматично при першому старті порожнього тому):

| Поле | Тип | Обовʼязкове | Примітка |
|---|---|---|---|
| id | BIGINT GENERATED ALWAYS AS IDENTITY, PK | так (генерує база) | клієнт id не передає |
| patient_code | VARCHAR(32) | так | код пацієнта, не порожній |
| department | VARCHAR(64) | так | відділення, не порожнє; поле фільтра |
| room | VARCHAR(16) | так | палата як рядок («12», «12А», «ІТ-3») |
| admission_date | DATE | так | дата надходження |
| discharge_date | DATE | ні (NULL = ще не виписаний) | CHECK: NULL або ≥ admission_date |
| outcome | VARCHAR(32) | так | одне з: на лікуванні, одужання, покращення, переведення, летальний наслідок |

Індекси: первинний ключ по `id`; `idx_admissions_department_id (department, id)`: обслуговує
фільтр за відділенням і одночасно порядок `ORDER BY id` для пагінації без окремого сортування.

Чому такі типи:
- `BIGINT IDENTITY`: послідовний ключ без колізій між репліками, ID генерує база, а не процес (сервіс без стану).
- `DATE`, а не `TIMESTAMP`: у завданні лише дати, часовий пояс не потрібен, порівняння «не раніша» точне.
- `room` рядком: палати бувають із літерами.
- `VARCHAR(n)` із межами: верхня межа довжини перевіряється і в сервісі, і в базі.
- Правило варіанта продубльоване як `CHECK` у базі: база не пропустить некоректні дані, навіть якщо їх запише
  не сервіс. Ця перевірка є страховкою; клієнт отримує 400 від сервісу, а не 500 від бази.
- Поле `outcome` обовʼязкове, а виписка може бути порожньою, тому для ще не виписаного пацієнта
  використовується значення `на лікуванні`. Це проєктне рішення.

## 2. Таблиця API

Формат помилки валідації (400): `{"error": "validation_error", "details": [{"field": "...", "message": "..."}]}`.
Пагінація: `limit` за замовчуванням **20**, верхня межа **100**, `offset` ≥ 0 (до 10⁹). Значення поза межами дають 400, а не мовчазне обрізання.

| Ендпоінт | Метод | Тіло запиту | Тіло відповіді | Успіх | Помилки |
|---|---|---|---|---|---|
| `/admissions` | POST | `patient_code, department, room, admission_date, discharge_date?, outcome` | створений запис з `id` (заголовок `Location`) | 201 | 400 невалідні дані: поле і причина; клієнт передав `id` або зайве поле |
| `/admissions?limit&offset&department` | GET | нема | `{"items": [...], "total": N, "limit": L, "offset": O}`; `total` враховує фільтр | 200 | 400 некоректні `limit`/`offset`/`department` |
| `/admissions/{id}` | GET | нема | запис | 200 | 404 запис не існує (і нечисловий id) |
| `/admissions/{id}` | PUT | усі поля, повна заміна | оновлений запис | 200 | 400 невалідні дані; 404 запис не існує |
| `/admissions/{id}` | DELETE | нема | порожнє | 204 | 404 (також при повторному видаленні) |
| `/healthz` | GET | нема | `{"status": "ok"}` | 200 | 503 база недоступна |

Валідація (на боці сервісу): рядки не порожні й не довші за межу, дати у форматі `YYYY-MM-DD` (число замість рядка відхиляється),
`outcome` зі списку, `discharge_date` або `null`/відсутня, або не раніша за `admission_date`; зайві поля відхиляються.
Якщо база недоступна під час запиту, сервіс повертає 503, а не 500.

      - "${LB_PORT:-8080}:80"    # єдина точка входу ззовні

      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro

### nginx/nginx.conf
```nginx
worker_processes auto;
events { worker_connections 4096; }

http {
    # up= показує, яка саме репліка обслужила запит (підтвердження розподілу)
    log_format lb '$remote_addr [$time_local] "$request" $status '
                  'rt=$request_time urt=$upstream_response_time up=$upstream_addr';
    access_log /dev/stdout lb;

    # Імʼя web розвʼязується Docker DNS у всі адреси реплік під час старту nginx.
    # Після зміни кількості реплік потрібен `docker compose restart lb`.
    upstream web_pool {
        server web:8000;
        keepalive 64;
    }

    server {
        listen 80;

        # Ендпоінт, який нічого не робить: для перевірки самого генератора
        location = /noop {
            access_log off;
            default_type text/plain;
            return 200 "ok\n";
        }

        location / {
            proxy_pass http://web_pool;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
            proxy_connect_timeout 2s;
            proxy_read_timeout 30s;
            add_header X-Upstream $upstream_addr always;
        }
    }
}
```

| Вимога | Як виконано |
|---|---|
| Три сервіси | `db`, `web`, `lb` |
| Порт назовні лише в балансувальника | `ports` лише у `lb`; `web` і `db` у мережі `backend` без публікації |
| Кількість інстансів одним параметром | `WEB_REPLICAS` (`deploy.replicas`), блок сервісу не копіюється |
| База за імʼям сервісу | `DB_HOST: db` |
| Схема автоматично | `db/init.sql` у `docker-entrypoint-initdb.d` |
| Том під дані | `pgdata` |
| Пароль не в образі/compose/історії | лише `.env` (поза git) → змінна `POSTGRES_PASSWORD`; у Dockerfile немає `ARG`/`ENV` з паролем; у compose лише підстановка `${POSTGRES_PASSWORD:?...}` |
| Залежність за станом бази | `depends_on: condition: service_healthy`; healthcheck бази через `pg_isready` по TCP |
| Сервіс чекає на базу | запуск після healthy-бази + пул зʼєднань з перепідключенням; `/healthz` віддає 503, доки бази нема |

| Ліміти варіанта | `cpus: "1"`, `memory: 512M` |
| Без стану в памʼяті | усе в PostgreSQL; пул зʼєднань не є станом даних |

## 8. Розрахунки

Заповнюються з виводу `python scripts/calc.py`.

**Прискорення і Карп-Флатт.** S = X₂ / X₁ (досягнута пропускна здатність на двох інстансах до одного на тому самому рівні),
e = (1/S − 1/N) / (1 − 1/N); N = 2 → e = (1/S − 0.5) / 0.5.
На рівні ⟨ЗАПОВНИТИ⟩: S = ⟨ЗАПОВНИТИ⟩ / ⟨ЗАПОВНИТИ⟩ = ⟨ЗАПОВНИТИ⟩; e = (1/⟨ЗАПОВНИТИ⟩ − 0.5) / 0.5 = ⟨ЗАПОВНИТИ⟩. Спільна складова: ⟨ЗАПОВНИТИ⟩.
На рівнях, де один інстанс ще тримав інтенсивність, S ≈ 1 і e ≈ 1 не означає поганого масштабування: другий інстанс просто не був потрібен.

**Закон Літтла** (1 інстанс, 100 req/s): L = λ·W.
λ = ⟨ЗАПОВНИТИ⟩ req/s, W = ⟨ЗАПОВНИТИ⟩ с, λ·W = ⟨ЗАПОВНИТИ⟩, виміряне L (середнє за вікном різниці відправлених і завершених) = ⟨ЗАПОВНИТИ⟩,
розбіжність = |L − λ·W| / L · 100% = ⟨ЗАПОВНИТИ⟩%.

**Відкритий і закритий контур.** Рівень ⟨ЗАПОВНИТИ⟩ req/s; concurrency закритого контуру = виміряне L відкритого = ⟨ЗАПОВНИТИ⟩.

| Контур | Досягнута, req/s | p95, мс |
|---|---|---|
| Відкритий | ⟨ЗАПОВНИТИ⟩ | ⟨ЗАПОВНИТИ⟩ |
| Закритий | ⟨ЗАПОВНИТИ⟩ | ⟨ЗАПОВНИТИ⟩ |

Пояснення: у закритому контурі нове навантаження надходить лише після відповіді, тому кількість запитів у системі не може
перевищити фіксовану concurrency, а черга не росте: система сама підлаштовує інтенсивність під свою пропускну здатність
(це неявний зворотний звʼязок). У відкритому контурі запити надходять незалежно від відповідей, при інтенсивності
вище за пропускну здатність черга росте, і затримка разом із нею. Закритий контур тому показує меншу затримку на тому ж сервісі,
але приховує перевантаження («coordinated omission»).

1. **Створення таблиці кодом сервісу при старті (`CREATE TABLE IF NOT EXISTS`).** Відхилено: при кількох репліках вони гонилися б за DDL;
   схема в `docker-entrypoint-initdb.d` виконується один раз, до появи будь-якого вебінстанса.
2. **Кілька воркерів uvicorn в одному контейнері.** Відхилено: контейнеру видано 1 CPU, воркери конкурували б за ядро,
   а масштабування реплік стенду стало б неочевидним для розрахунку Карпа-Флатта (N інстансів ≠ N процесів). Масштабуємо контейнерами.
3. **ORM (SQLAlchemy) замість прямого psycopg.** Відхилено: запити прості, ORM додає накладні витрати CPU на кожен запит і більше залежностей у образі,
   що спотворило б вимір пропускної здатності.
4. **Базовий образ alpine.** Відхилено: образ варіанта `python:3.12-slim`; alpine (musl) дає менший розмір, але ризик із бінарними колесами
   (uvloop, psycopg-binary) і інший профіль продуктивності, що ускладнює порівняння.
5. **`proxy_pass` зі змінною і `resolver` у nginx (розвʼязання імені на кожен запит).** Відхилено: додає DNS-пошук у гарячий шлях і плутає вимірювання;
   обрано `upstream` з `keepalive`, ціна: після зміни кількості реплік потрібен `docker compose restart lb`.
6. **Невалідні `limit`/`offset` мовчки обрізати.** Відхилено: клієнт не дізнається про помилку; обрано явний 400 з назвою поля.
7. **Сторонні генератори (wrk, k6, locust).** Відхилено умовою завдання: генератор власний, з відкритим контуром.

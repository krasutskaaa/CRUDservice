# Звіт. Лабораторна робота 1, варіант 12: епізод госпіталізації (`/admissions`)

Стек: Python 3.12 (образ `python:3.12-slim`), FastAPI + uvicorn, psycopg 3 з пулом зʼєднань, PostgreSQL 16, nginx 1.27, Docker Compose.
Параметри варіанта: фінальний образ `python:3.12-slim`, ліміти контейнера сервісу 1 CPU / 512 МБ, додаткова вимога: healthcheck без curl і wget в образі.

Умови вимірювань: Windows, Docker Desktop (віртуальна машина Docker має 3.7 ГБ памʼяті). Генератор навантаження і весь стенд працюють на одному ноутбуці,
тому на верхніх рівнях вони конкурують за ядра. Модель процесора, кількість ядер і RAM: Intel(R) Core(TM) i5-10300H CPU @2.50 GHz, 4, 8Gb DDR4.

## 1. Схема таблиці

Таблиця `admissions` (файл `db/init.sql`, накочується автоматично при першому старті порожнього тому):

| Поле | Тип | Обовʼязкове | Примітка |
|---|---|---|---|
| id | BIGINT GENERATED ALWAYS AS IDENTITY, PK | так (генерує база) | клієнт id не передає |
| patient_code | VARCHAR(32) | так | код пацієнта, не порожній |
| department | VARCHAR(64) | так | відділення, не порожнє; поле фільтра |
| room | VARCHAR(16) | так | палата як рядок («12», «12А») |
| admission_date | DATE | так | дата надходження |
| discharge_date | DATE | ні (NULL = ще не виписаний) | CHECK: NULL або ≥ admission_date |
| outcome | VARCHAR(32) | так | одне з: на лікуванні, одужання, покращення, переведення, летальний наслідок |

Індекси: первинний ключ по `id`; `idx_admissions_department_id (department, id)`. Він обслуговує фільтр за відділенням і водночас порядок `ORDER BY id`, тому пагінація не потребує окремого сортування.

Чому такі типи:
- `BIGINT IDENTITY`: ідентифікатор генерує база, а не процес, тому сервіс не тримає стану і кілька реплік не дають колізій.
- `DATE`, а не `TIMESTAMP`: у завданні лише дати, часовий пояс не потрібен, порівняння «не раніша» точне.
- `room` рядком: палати бувають із літерами.
- `VARCHAR(n)` із межами: верхня межа довжини перевіряється і в сервісі, і в базі.
- Правило варіанта продубльоване як `CHECK` у базі як страховка: клієнт отримує 400 від сервісу, а не 500 від бази.
- Поле `outcome` обовʼязкове, а виписка може бути порожньою, тому для ще не виписаного пацієнта використовується значення `на лікуванні`. Це проєктне рішення автора.

## 2. Таблиця API

Формат помилки валідації (400): `{"error": "validation_error", "details": [{"field": "...", "message": "..."}]}`.
Пагінація: `limit` за замовчуванням **20**, верхня межа **100**, `offset` ≥ 0. Значення поза межами дають 400, а не мовчазне обрізання.

| Ендпоінт | Метод | Тіло запиту | Тіло відповіді | Успіх | Помилки |
|---|---|---|---|---|---|
| `/admissions` | POST | `patient_code, department, room, admission_date, discharge_date?, outcome` | створений запис з `id` (заголовок `Location`) | 201 | 400: невалідні дані (поле і причина), зайве поле, `id` від клієнта |
| `/admissions?limit&offset&department` | GET | нема | `{"items": [...], "total": N, "limit": L, "offset": O}`; `total` враховує фільтр | 200 | 400: некоректні `limit`/`offset`/`department` |
| `/admissions/{id}` | GET | нема | запис | 200 | 404: запису немає (також нечисловий id) |
| `/admissions/{id}` | PUT | усі поля, повна заміна | оновлений запис | 200 | 400: невалідні дані; 404: запису немає |
| `/admissions/{id}` | DELETE | нема | порожнє | 204 | 404: запису немає, зокрема при повторному видаленні |
| `/healthz` | GET | нема | `{"status": "ok"}` | 200 | 503: база недоступна |

Валідація на боці сервісу: рядки не порожні й не довші за межу, дати у форматі `YYYY-MM-DD` (число замість рядка відхиляється), `outcome` зі списку,
`discharge_date` або `null`/відсутня, або не раніша за `admission_date`; зайві поля відхиляються. Якщо база недоступна під час запиту, сервіс повертає 503, а не 500.

## 3. Dockerfile, .dockerignore, docker-compose.yml

### Dockerfile
```dockerfile
# syntax=docker/dockerfile:1

# ---------- Стадія 1: збірка залежностей ----------
FROM python:3.12-slim AS builder
WORKDIR /build
COPY app/requirements.txt .
# Усі пакети мають готові колеса (psycopg[binary], uvloop, httptools),
# тому компілятор не потрібен навіть тут.
RUN pip install --no-cache-dir --target=/install -r requirements.txt

# ---------- Стадія 2: фінальний образ ----------
FROM python:3.12-slim AS final
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PYTHONPATH=/opt/deps \
    PORT=8000
# Із фінальної стадії прибираємо засоби збірки пакетів
RUN python -m pip uninstall -y pip setuptools wheel || true
COPY --from=builder /install /opt/deps
WORKDIR /srv
COPY app/main.py app/healthcheck.py ./
USER 10001:10001
EXPOSE 8000
# Один воркер на контейнер: контейнеру видається 1 CPU, масштабуємо репліками.
CMD ["python", "-m", "uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--workers", "1", "--loop", "uvloop", "--http", "httptools", "--no-access-log", \
     "--timeout-keep-alive", "75"]
```

```yaml
name: admissions-lab

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: ${POSTGRES_DB:-admissions}
      POSTGRES_USER: ${POSTGRES_USER:-admissions}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?задайте POSTGRES_PASSWORD у файлі .env}
    volumes:
      - pgdata:/var/lib/postgresql/data
      # схема накочується автоматично при ініціалізації порожнього тому
      - ./db/init.sql:/docker-entrypoint-initdb.d/001-schema.sql:ro
    healthcheck:
      # -h 127.0.0.1: тимчасовий сервер ініціалізації слухає лише unix-сокет,
      # тож перевірка по TCP спрацьовує лише коли база справді готова
      test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 2s
      timeout: 3s
      retries: 30
    networks: [backend]

  web:
    build: .
    image: admissions-web:lab1
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      DB_NAME: ${POSTGRES_DB:-admissions}
      DB_USER: ${POSTGRES_USER:-admissions}
      DB_PASSWORD: ${POSTGRES_PASSWORD:?задайте POSTGRES_PASSWORD у файлі .env}
      PORT: "8000"
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      # без curl і wget: Python зі стандартної бібліотеки образу
      test: ["CMD", "python", "/srv/healthcheck.py"]
      interval: 3s
      timeout: 3s
      retries: 10
      start_period: 3s
    deploy:
      replicas: ${WEB_REPLICAS:-1}
      resources:
        limits:
          cpus: "1"
          memory: 512M
    networks: [backend]          # портів назовні немає

  lb:
    image: nginx:1.27-alpine
    ports:
      - "${LB_PORT:-8080}:80"    # єдина точка входу ззовні
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      web:
        condition: service_healthy
    networks: [backend]

networks:
  backend:

volumes:
  pgdata:
```

### nginx/nginx.conf
```nginx
worker_processes auto;
events { worker_connections 4096; }

http {
    # up= показує, яка саме репліка обслужила запит (підтвердження розподілу)
    log_format lb '$remote_addr [$time_local] "$request" $status '
                  'rt=$request_time urt=$upstream_response_time up=$upstream_addr';
    access_log /dev/stdout lb;

    # Імʼя web розвʼязується Docker DNS у всі адреси реплік під час старту nginx.
    # Після зміни кількості реплік потрібен `docker compose restart lb`.
    upstream web_pool {
        server web:8000 max_fails=0;
        keepalive 64;
    }

    server {
        listen 80;

        # Ендпоінт, який нічого не робить: для перевірки самого генератора
        location = /noop {
            access_log off;
            default_type text/plain;
            return 200 "ok\n";
        }

        location / {
            proxy_pass http://web_pool;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
            proxy_connect_timeout 2s;
            proxy_read_timeout 30s;
            add_header X-Upstream $upstream_addr always;
        }
    }
}
```

Відповідність вимогам:

| Вимога | Як виконано |
|---|---|
| Три сервіси | `db`, `web`, `lb` |
| Порт назовні лише в балансувальника | `ports` лише у `lb`; `web` і `db` у мережі `backend` без публікації |
| Кількість інстансів одним параметром | `WEB_REPLICAS` (`deploy.replicas`), блок сервісу не копіюється |
| База за імʼям сервісу | `DB_HOST: db` |
| Схема автоматично | `db/init.sql` у `docker-entrypoint-initdb.d` |
| Том під дані | `pgdata` |
| Пароль не в образі, історії збірки і compose | лише `.env` (поза git) → змінна `POSTGRES_PASSWORD`; у Dockerfile немає `ARG`/`ENV` з паролем; у compose тільки підстановка `${POSTGRES_PASSWORD:?...}` |
| Залежність запуску за станом бази | `depends_on: condition: service_healthy`; healthcheck бази через `pg_isready` по TCP (`-h 127.0.0.1`) |
| Сервіс чекає на базу | запуск після healthy-бази, пул зʼєднань сам перепідключається; `/healthz` віддає 503, доки бази немає |
| Без встановлення пакетів при старті | залежності ставляться у стадії збірки; `CMD` лише запускає uvicorn |
| Збірка багатоетапна, у фінальній стадії немає засобів збірки | залежності збираються в стадії `builder`; у фінальній стадії видалено pip, setuptools, wheel; компіляторів у `python:3.12-slim` немає |
| Ліміти варіанта | `cpus: "1"`, `memory: 512M` |
| Без стану в памʼяті | усе в PostgreSQL |

## 5. Вимірювання під навантаженням

**Генератор** (`loadgen/loadgen.py`, лише стандартна бібліотека Python) працює у відкритому контурі. Задана інтенсивність ділиться між процесами за кількістю ядер.
Кожен процес наперед обчислює моменти відправки `t_k = t0 + k/rate` і віддає кожен запит пулу потоків, тож цикл планування не чекає на відповіді.
Затримка міряється від запланованого моменту відправки, тому черга всередині самого генератора теж видима в числах.
«Досягнута інтенсивність» це кількість відповідей, завершених у вимірювальному вікні, поділена на тривалість вікна (воно може трохи перевищувати задану, бо у вікні завершуються й запити, що стояли в черзі).
Перцентилі рахуються за всіма запитами вікна. Частка не-2xx подається окремо.

**Сценарій:** `GET /admissions/{id}`, ідентифікатор береться з 100 записів, занесених перед серією (`loadgen/seed.py`). Рівні 10, 100 і 500 req/s, прогрів 10 с (не входить у результат), вимір 30 с, кожен рівень тричі, у таблицях медіани. Команда одного прогону:

```
python loadgen/loadgen.py --rate 100 --warmup 10 --duration 30 --instances 1 --out results/raw/open_n1_r100_run1.json
```

Уся серія: `python scripts/run_series.py --instances 1` і `python scripts/run_series.py --instances 2`.
Додаткові рівні: `python scripts/run_series.py --instances N --rates 750 1000 1500`. Вони потрібні, бо на 500 req/s один інстанс виявився ще справним, а розрахунки 1 і 3 вимагають рівня, де він не тримає навантаження.

**Перевірка генератора проти ендпоінта, що нічого не робить** (`/noop` у nginx, команда `python scripts/run_series.py --instances 1 --selfcheck`):

| 10 | 10.0 | 4.87 | 1.35 |
| 100 | 100.0 | 5.04 | 1.23 |

## 7. Висновок

**Рівень, на якому сервіс перестав тримати інтенсивність.** Один інстанс тримає 10, 100, 500 і 750 req/s. На 1000 req/s він на межі: досягнута 999.8, 926.6 і 1000.3 у трьох прогонах.
На **1500 req/s** він не тримає: досягнуто 1206.4 (прогони 1101.9-1221.0), p50 зріс до 7269 мс (проти 2 мс на 500), p95 до 11092 мс, а середня кількість запитів у системі L ≈ 8326.
Це видно з трьох речей одночасно: досягнута нижча за задану, затримка виросла на три порядки, черга накопичується. Пропускна здатність одного інстанса приблизно 1.1-1.2 тис. req/s.
Рівень 500 req/s, який завдання виділяє як можливо недосяжний, один інстанс у фінальній серії досягає.

**Що змінилось після додавання другого інстанса.** Два інстанси тримають усі рівні, включно з 1500 req/s (досягнута 1499.6). На 500 req/s p95 впав з 36.4 до 3.2 мс, p99 з 156.3 до 21.5 мс.
На 1000 req/s p95 впав з 409.8 до 38.9 мс. На 1500 req/s p95 впав з 11092 до 214.3 мс, а p99 з 11221 до 301.8 мс. Не-2xx скрізь нуль.

**Складова, що лишилась спільною для обох інстансів.**  Із наявних даних: обидва `web` на сплеску працюють на 81-90% свого ядра (тобто це ще не стеля), `db` займає 21-24% CPU, `lb` 18-30%.
Спільними для обох інстансів лишаються PostgreSQL (одна), nginx (один) і процесор самого ноутбука, на якому працюють також віртуальна машина Docker і генератор навантаження. Найімовірніше, що саме процесор машини стане спільним обмеженням,
але це припущення, яке не перевірено: на жодному з рівнів друга конфігурація не досягла своєї межі, тому спільне обмеження в експерименті не проявилось.

**Обмеження і спостереження, які не вдалося пояснити.**
1. У першій серії (до виправлень, розділ 11) один інстанс на 500 req/s давав 285.6-334.7 req/s при p50 10-15 с, `web` був близько 99% CPU. У фінальній серії той самий стенд на тому самому рівні тримає 500 req/s і навіть 1200 req/s.
   Яка зміна або яка зовнішня умова (живлення ноутбука, фонові процеси, синхронізація OneDrive) цю різницю дала, я не встановила. У таблицях цього звіту використані дані фінальної серії; ранні числа наведено лише як окреме спостереження (сирі файли ранньої серії перезаписані, збереглося діагностичний прогін `results/raw/diag_n1_r500.json`).
2. Генератор і стенд працюють на одній машині, тому абсолютні цифри пропускної здатності залежать від цієї машини.

## 8. Розрахунки

**1. Прискорення і метрика Карпа-Флатта.** S = X₂ / X₁, де X — досягнута пропускна здатність на тому самому рівні; e = (1/S − 1/N) / (1 − 1/N), для N = 2: e = (1/S − 0.5) / 0.5.
У всіх запусках частка не-2xx нульова, тому пропускна здатність за 2xx збігається з наведеною.

| Рівень, req/s | X₁ | X₂ | S | e |
|---|---|---|---|---|
| 10 | 10.0 | 10.0 | 1.000 | 1.000 |
| 100 | 100.0 | 100.0 | 1.000 | 1.000 |
| 500 | 499.9 | 499.9 | 1.000 | 1.000 |
| 750 | 749.8 | 749.9 | 1.000 | 1.000 |
| 1000 | 999.8 | 999.9 | 1.000 | 1.000 |
| 1500 | 1206.4 | 1499.6 | 1.243 | 0.609 |

Підстановка для рівня 1500: S = 1499.6 / 1206.4 = 1.243; e = (1/1.243 − 0.5) / 0.5 = (0.8045 − 0.5) / 0.5 = 0.609.
На рівнях до 1000 включно обидві конфігурації тримають задану інтенсивність, тому S = 1.000 і e = 1.000 є наслідком побудови (відношення двох однакових заданих значень), а не оцінкою масштабування. Корисні лише дані рівня 1500.
Але й там два інстанси ще не насичені (досягнута 1499.6 при заданих 1500), тому S = 1.243 це нижня оцінка прискорення, а e = 0.609 верхня оцінка частки роботи без виграшу. Спільна складова стенду: див. розділ 7.

**2. Закон Літтла** (1 інстанс, 100 req/s). L = λ·W; розбіжність = |L_вим − λ·W| / L_вим · 100%. L_вим це середнє за вікном число запитів у системі, обчислене з записів генератора як інтеграл різниці відправлених і завершених.

| Прогін | λ, req/s | W, с | λ·W | L виміряне | Розбіжність, % |
|---|---|---|---|---|---|
| 1 | 100.00 | 0.01294 | 1.2943 | 1.4054 | 7.90 |
| 2 | 100.00 | 0.00410 | 0.4097 | 0.4097 | 0.00 |
| 3 | 100.00 | 0.00388 | 0.3881 | 0.3881 | 0.00 |

Для прогону з медіанним W (прогін 2): λ = 100.00, W = 0.00410 с, λ·W = 0.4097, L = 0.4097, розбіжність 0.00%. Розбіжність 7.9% у першому прогоні: у ньому затримки були вищі (p95 47 мс), а середнє за вікном враховує запити на межах вікна.
L і W обчислені з одних і тих самих записів генератора, тому збіг майже тотожний, це перевірка узгодженості обліку, а не незалежне підтвердження.

**3. Відкритий і закритий контур.** Рівень 1500 req/s (перший, де один інстанс не тримає задану інтенсивність). Закритий контур: наступний запит іде після відповіді на попередній, фіксована кількість одночасних запитів.

| Контур | Досягнута, req/s | p95, мс |
|---|---|---|
| Відкритий, 1500 req/s | 1206.4 | 11092.0 |
| Закритий, 1000 одночасних запитів | 316.6 | 4825.2 |

Закритий контур, окремі прогони: 352.1, 316.6, 256.6 req/s; p95 4980.7, 4825.2, 4825.2 мс; p50 2494, 3217, 4164 мс (медіани взято по колонках окремо). У першому прогоні 1.25% відповідей не 2xx, в інших нуль; причину цих помилок не з'ясовано.
**Відхилення від умови завдання:** concurrency мала дорівнювати кількості запитів у відкритому контурі, тобто L ≈ 8326. Прогін із 8326 одночасними запитами я виконала (python scripts/run_closed.py --instances 1 --level 1500), але він не придатний для порівняння: у трьох прогонах 94.6-95.0% відповідей не були 2xx («досягнуто» 3200-3284 req/s складається здебільшого з швидких відмов), p50 близько 2.1 с. Це вимірювання не сервісу, а перевантаженого стенду разом із генератором (кожен одночасний запит у моєму генераторі це окремий потік із власним зʼєднанням). Причину відмов не з'ясовано: тип помилок (502, таймаут) я не досліджувала. Тому для порівняння використано 1000 одночасних запитів (змінено scripts/run_closed.py). Для довідки, генератор окремо перевірено на 1000 одночасних запитах проти /noop: досягнуто 9330 req/s, p95 94.7 мс, помилок немає.

Чому закритий контур показує меншу затримку на тому самому сервісі: у закритому контурі нове навантаження надходить тільки після відповіді, тож у системі не буває більше 1000 запитів і черга не росте. У відкритому запити надходять незалежно від відповідей, і при інтенсивності вище за пропускну здатність черга росте протягом усього прогону. За законом Літтла W ≈ L / X: відкритий 8326 / 1206 ≈ 6.9 с (виміряний p50 7.3 с), закритий 1000 / 316.6 ≈ 3.2 с (виміряний медіанний p50 3.2 с). Закритий контур, таким чином, підлаштовує інтенсивність під можливості сервісу й ховає перевантаження.

Чого я не пояснила: пропускна здатність у закритому контурі (≈317 req/s) майже вчетверо нижча, ніж у відкритому (1206 req/s) при тому самому сервісі, і прогони закритого контуру різняться між собою (257-352 req/s). Генератор причиною не є (перевірка проти /noop). Можливе пояснення: 1000 одночасних зʼєднань гірші для одного воркера uvicorn і пулу з 10 зʼєднань до бази, ніж черга у відкритому контурі, але це гіпотеза без перевірки.

## 9. Журнал перевірки

Команда: `python scripts/verify_cycle.py --persistence`. Скрипт виконав послідовність: готовність `/healthz` → створення запису (201) → невалідні створення (400: виписка раніше надходження, бракує поля, `id` від клієнта, невідомий результат) →
перелік із фільтром за відділенням і без (200), `limit=1000` (400) → читання за id (200) і неіснуючого (404) → заміна (200), невалідна заміна (400), заміна неіснуючого (404) → видалення (204) → повторне видалення (404) → читання видаленого (404) →
`down` і `up`: запис на місці (200) → зупинка бази: `/healthz` 503 → запуск бази: `/healthz` 200 → `down -v` і `up`: перелік порожній (`total` = 0).

Повний протокол запитів і відповідей: файл `results/verify_log.md` у репозиторії.

## 10. Додаткова вимога: healthcheck без curl і wget в образі

Реалізація: `app/healthcheck.py` (стандартна бібліотека `urllib`) викликає `GET /healthz` і виходить із кодом 0 лише при відповіді 200. У compose: `test: ["CMD", "python", "/srv/healthcheck.py"]`.
`/healthz` виконує `SELECT 1`, тож контейнер здоровий тільки поки доступна база. Образ `python:3.12-slim` не містить curl і wget, і в `Dockerfile` вони не встановлюються.

Підтвердження:
- `docker compose ps` показує `web` зі станом `Up ... (healthy)` (спостерігалось у виводі після підняття стенду);
- перевірка відсутності засобів: `docker compose exec web sh -c "command -v curl || echo curl: немає; command -v wget || echo wget: немає"`, результат: curl: немає, wget: немає
- при зупиненій базі перевірка повертає 503 (крок журналу з `--persistence`), а `web` перестає бути healthy.

## 11. Відкинуті рішення

1. **Створення таблиці кодом сервісу при старті (`CREATE TABLE IF NOT EXISTS`).** Відхилено: кілька реплік гонилися б за DDL; схема в `docker-entrypoint-initdb.d` виконується один раз, до появи будь-якого вебінстанса.
2. **Кілька воркерів uvicorn в одному контейнері.** Відхилено: контейнеру видано 1 CPU, воркери конкурували б за ядро, а N інстансів стенду перестали б означати N процесів, що псує розрахунок Карпа-Флатта. Масштабуємо контейнерами.
3. **ORM (SQLAlchemy) замість прямого psycopg.** Відхилено: запити прості, ORM додає накладні витрати CPU на кожен запит і більше залежностей в образі, що спотворило б вимір пропускної здатності.
4. **Базовий образ alpine.** Відхилено: образ варіанта `python:3.12-slim`; alpine (musl) дає менший розмір, але ризик із бінарними колесами (uvloop, psycopg-binary) і інший профіль продуктивності.
5. **`proxy_pass` зі змінною і `resolver` у nginx (розвʼязання імені на кожен запит).** Відхилено: додає DNS-пошук у гарячий шлях; обрано `upstream` з `keepalive`. Ціна: після зміни кількості реплік потрібен `docker compose restart lb`.
6. **Мовчазне обрізання невалідних `limit`/`offset`.** Відхилено: клієнт не дізнається про помилку; обрано явний 400 з назвою поля.
7. **Сторонні генератори (wrk, k6, locust).** Відхилено умовою завдання: генератор власний, з відкритим контуром.
8. **Закритий контур із concurrency ≈ 8326.** Спробу виконано, відхилено: понад 94% відповідей не 2xx, результат не придатний для порівняння; використано 1000 (розділ 8). Сирі файли спроби: results/closed_8326_attempt/.

**Проблема, виявлена під час роботи: 502 на двох інстансах.** У першій серії з двома інстансами на 500 req/s частка не-2xx була 1.8%, 9.3% і 6.6% (у запису одного з прогонів 502: 273, 1397 і 995 із 20000 відповідей по прогонах; на одному інстансі помилок не було).
Лог nginx містив спершу `recv() failed (104: Connection reset by peer)` і `upstream prematurely closed connection` від обох реплік, потім `no live upstreams` (за замовчуванням nginx вилучає репліку на 10 с після першої помилки).
Вжито двох змін одночасно: `--timeout-keep-alive 75` для uvicorn (довше, ніж у nginx) і `max_fails=0` в `upstream`. Після них і повторення серій 502 зникли. Яка саме зміна допомогла, я не розділяла.
Причину розривів зʼєднань (таймаут keep-alive uvicorn чи перевантаження) однозначно не підтверджено. Сирі файли тієї серії перезаписані повторними прогонами, цифри наведено з виводу консолі.

**Проблеми середовища Windows, виправлені в скриптах:** URL з кирилицею (`?department=кардіологія`) кодується у відсотковий формат; текстові файли пишуться в UTF-8 (`PYTHONUTF8=1`), бо за замовчуванням Python на Windows використовує cp1251.
Також пароль у `.env` треба задавати до першого запуску стенду: пароль зберігається в томі бази, і його зміна без `docker compose down -v` дає `password authentication failed`.
